# Task C3: preprocess-cost probe for SPR candidate topologies

## What was measured

`preprocess_families()` (`gpurax/recon/incremental.py`) wraps the existing whole-dataset
CPU-side Rust preprocessor `preprocess_dataset` (`gpurec/core/scheduling/batching.py`), which
in turn calls `gpurec_preprocess.preprocess_dataset` (native module, no CUDA required). This is
the function an SPR search would call to turn a batch of candidate gene-tree topologies into
gpurec input (CCPs + batch/wave layout) before scoring them.

Benchmark (`tests/gpurax/test_recon_cost.py::test_preprocess_throughput_recorded`, fixtures
`tests/gpurax/fixtures/species.nwk` — 4 species — and `gene.nwk` — 4-taxon gene topology):
200 copies of the same tiny topology are preprocessed in a single `preprocess_families` call,
simulating the size of a neighbor batch generated by one SPR step.

## Measured numbers

Ran via pytest (`pytest tests/gpurax/test_recon_cost.py -v -m benchmark`):

- **8991.3 topologies/s** (single pytest-invoked call, includes native-module first-load cost).

Ran manually (repo-root Python, three warmed-up trials after one throwaway warmup call so the
native module is already loaded):

| trial | wall time (200 topologies) | topologies/s |
|-------|-----------------------------|--------------|
| 1     | 0.0266 s                    | 7506.9       |
| 2     | 0.0251 s                    | 7961.3       |
| 3     | 0.0250 s                    | 7989.0       |

Median (warm): **~7961 topologies/s**, i.e. ~0.126 ms/topology for a 200-way batched call on
this 4-taxon fixture.

Both numbers are real measurements (`time.perf_counter`), not estimates.

## Decision

**Keep `preprocess_dataset` as-is; do not build the incremental (`build_family_ccp` +
`replan_batches`) route.**

At ~8-9k topologies/s batched, a realistic SPR neighbor batch (tens to a few hundred candidate
topologies per step) costs on the order of single-digit milliseconds to preprocess — negligible
next to the GPU likelihood-evaluation cost per batch (which is what SPR search is actually
bottlenecked on; see project memory on wave/FP kernel timings, tens/hundreds of ms per family at
realistic S). There is no throughput problem to justify the added complexity of incremental
per-family reuse across SPR steps.

## Caveats

- The benchmark fixture topologies are intentionally tiny (4 taxa, 4 species) per the brief —
  this measures the *fixed/per-call* overhead of the preprocessor (native module dispatch, JSON
  marshalling, tensor construction), not how cost scales with gene-family size (number of taxa)
  or species-tree size. If real workloads use much larger gene families or a much larger species
  tree, this number should be re-measured on realistic sizes before fully closing the risk.
- All 200 entries in the benchmark are copies of one topology (same CCP), so the native
  preprocessor may hit favorable cache/JIT behavior it wouldn't for 200 genuinely distinct
  candidate topologies. The measured number is still a fair proxy for the fixed dispatch/
  marshalling overhead, which is the part relevant to "is this fast enough to call every SPR
  step," but the correctness test (`test_incremental_matches_full`) only exercises 4 duplicate
  topologies too — no distinct-topology-count stress test was run here.
- If future profiling on realistic gene-family/species-tree sizes shows preprocessing becoming
  a bottleneck relative to GPU scoring, revisit and implement the incremental
  `build_family_ccp`/`replan_batches` path described in the brief, and re-measure.
